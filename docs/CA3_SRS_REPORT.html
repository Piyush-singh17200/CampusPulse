1. Introduction

The introduction to this Software Requirements Specification (SRS) provides an authoritative technical overview of CampusPulse, adhering to IEEE Std 830-1998 guidelines.

1.1 Purpose

The purpose of this document is to define the functional, operational, performance, security, and interface specifications for CampusPulse. It describes all system behaviors and architectural boundaries required by software engineers to implement, test, deploy, and maintain the system. The intended audience includes the course instructors for INT257/INT252, student developers, QA automation testers, and university IT administrators.

1.2 Scope

CampusPulse is a cloud-native, multi-tenant campus event discovery and governance platform designed for universities. The platform will:

  • Provide role-isolated dashboard workspaces for Students, Club Administrators, College Administrators, and Platform Super Admins.
  • Enforce logical multi-tenant database isolation, enabling multiple colleges to operate on a shared PostgreSQL instance without cross-tenant data leaks.
  • Allow student clubs to draft event proposals, upload promotional artwork, and automatically extract dates and venues via server-side OCR.
  • Programmatically detect schedule collisions and duplicate proposals across campus venues before college approval.
  • Issue tamper-evident, dynamic HMAC-SHA256 QR attendance passes to registered students and verify tickets via browser-based camera scanning.
  • Provide a unified settings center with Argon2id password rotation, active session revocation, and dark mode theming.

The software will not process monetary ticket payments or store personal biometric information.

1.3 Definitions, Acronyms, and Abbreviations

  • Argon2id: A memory-hard key derivation function for secure password hashing (RFC 9106).
  • Better Auth: Modern TypeScript authentication framework providing cookie-based session management.
  • DFD: Data Flow Diagram representing processes, data stores, and external entities.
  • FSM: Finite State Machine governing lifecycle transitions for events and registrations.
  • HMAC: Hash-Based Message Authentication Code used to sign dynamic QR check-in tokens.
  • OCR: Optical Character Recognition for extracting text from promotional posters via Tesseract.js.
  • RBAC: Role-Based Access Control enforcing permissions based on user roles.

2. General Description

2.1 Product Perspective

CampusPulse operates as a modern cloud-native system replacing informal WhatsApp groups, physical sign-up desks, and unverified Google Forms. It runs as a self-contained Next.js application interfacing with Neon PostgreSQL 17 and Supabase S3 storage.

+---------------------------------------------------------------------------------------+ | CAMPUSPULSE SYSTEM | | | | [ User Workspaces ] | | - Student Portal (/student) - Club Organizer Console (/club) | | - College Administration (/college) - Platform Governance (/platform) | | - Unified Settings Center (/account) - Public Discovery Portal (/) | +-------------------------------------------+-------------------------------------------+ | +------------------+------------------+ | | v v +-----------------------------------------------+ +------------------------------------+ | NEON POSTGRESQL 17 | | SUPABASE S3 STORAGE | | - 19 Relational Database Models | | - Private event poster buckets | | - Atomic Token-Bucket Rate Limiter | | - Presigned upload/read URLs | | - Immutable Audit Logging Engine | | - Magic-byte validated media | +-----------------------------------------------+ +------------------------------------+
Figure 1: Product Perspective & System Context

2.2 Product Functions

  • Multi-Tenant Management: Provisioning university organizations with unique slugs, domains, and timezones.
  • Identity & Sessions: Email-domain matching registration, Argon2id passwords, and remote session revocation.
  • Event Operations: Multi-step drafting, S3 poster storage, Tesseract OCR analysis, and clash detection.
  • Discovery & Recommendation: Deterministic ranking using student academic interests and recency decay.
  • Cryptographic Attendance: HMAC-signed QR check-in passes verified via live camera scanning with atomic single check-in commits.

2.3 User Characteristics

  • Student: Accesses campus events on mobile/desktop; registers for events, views personalized schedules, generates QR check-in passes, and submits verified feedback.
  • Club Admin: Organizes student clubs; creates event proposals, uploads posters, monitors ticket capacity, and operates the live camera scanner at venue entrances.
  • College Admin: University faculty/deans; moderates proposals, reviews room clash warnings, manages club statuses, and oversees college audit logs.
  • Super Admin: Platform operator; provisions college tenants, manages global user permissions, and monitors system audit history.

2.4 General Constraints

The system is designed under a zero-cost free-tier deployment constraint: Vercel Hobby + Neon PostgreSQL Free Tier (0.5 GB) + Supabase Storage Free Tier (1 GB). All operations must preserve tenant isolation; cross-tenant queries must return HTTP 404.

2.5 Assumptions and Dependencies

Users require modern web browsers supporting HTML5 getUserMedia for live camera scanning. Relational database connectivity depends on Neon PostgreSQL 17 serverless availability with SSL enabled.

3. Specific Requirements

3.1 External Interface Requirements

3.1.1 User Interfaces

The UI is fully responsive across mobile (360px), tablet (768px), and desktop (1440px) breakpoints. It features semantic light and dark themes toggled via /account, with pre-hydration scripts eliminating visual flash.

3.1.2 Hardware Interfaces

Interfaces with client device cameras via HTML5 MediaDevices.getUserMedia for real-time QR code decoding via jsQR.

3.1.3 Software Interfaces

  • Neon PostgreSQL 17: Connected via Prisma PgAdapter using pooled connections with mandatory SSL encryption (sslmode=require).
  • Supabase S3 Storage: Interfaced via AWS S3 SDK for presigned upload URLs and secure object streaming.
  • Tesseract.js Engine: In-process WebAssembly/Node workers for optical character recognition on event poster images.

3.1.4 Communications Interfaces

All traffic is strictly HTTPS (TLS 1.3). Mutations utilize Next.js Server Actions with strict Origin and Host verification to eliminate CSRF risks. Exports deliver RFC 5545 iCalendar (.ics) and RFC 4180 CSV files.

3.2 Functional Requirements

3.2.1 Multi-Tenant Organization & Tenant Provisioning

  • Introduction: Enables Super Admins to provision and govern university tenants.
  • Inputs: name (2-160 chars), slug (2-80 chars, lowercase alphanumeric with hyphens), shortName, primaryDomain, timezone (valid IANA string).
  • Processing: Verify caller is SUPER_ADMIN. Validate timezone. Check slug and domain uniqueness. Insert College record in ACTIVE status. Write COLLEGE_CREATED audit log.
  • Outputs: Provisioned College record; immediate availability for student registration.
  • Error Handling: If caller unauthorized: throw ActorNotAuthorizedError (403). If slug/domain exists: throw DomainError("CONFLICT", 409).

3.2.2 User Authentication, Argon2id Passwords & Session Governance

  • Introduction: Manages user registration, credential hashing, login, password rotation, and active session termination.
  • Inputs: Registration credentials, login credentials, currentPassword, newPassword (min 8 chars, 1 uppercase, 1 lowercase, 1 number), sessionId.
  • Processing: Hash passwords with memory-hard Argon2id. Issue secure HTTP-only cookies. On password change: verify existing hash, update credential, purge remote sessions, record PASSWORD_CHANGED audit log.
  • Outputs: Authenticated session cookie; active sessions list in /account.
  • Error Handling: Return unified "Invalid email or password" error to prevent enumeration.
3

3.2.3 Student Event Discovery, Search & Recommendations

  • Introduction: Provides categorized event search with deterministic recommendation scoring.
  • Inputs: Search string q, category slug, date filter, page number.
  • Processing: Query Event table scoped to student's verified collegeId. Compute recommendation score based on interest overlap (+30 pts), department match (+20 pts), and recency decay. Exclude full, cancelled, or registered events.
  • Outputs: Paginated event catalog with live capacity and registration status indicators.
  • Error Handling: Graceful fallback to default upcoming events on empty query results.

3.2.4 Event Capacity, Registration & Cancellation FSM

  • Introduction: Governs event ticket registrations with atomic concurrency locks.
  • Inputs: eventId (UUID).
  • Processing: Within an atomic PostgreSQL transaction: lock event row, verify status is PUBLISHED, check student not already registered, verify confirmed count is less than capacity, insert EventRegistration record in CONFIRMED status, write REGISTRATION_STATUS_CHANGED audit log.
  • Outputs: Confirmed EventRegistration record; updated capacity counter.
  • Error Handling: If at capacity: throw DomainError("EVENT_FULL", 409). If duplicate: throw DomainError("DUPLICATE_REGISTRATION", 409).

3.2.5 Event Proposal Drafting, Conflict Detection & Moderation Queue

  • Introduction: Enables clubs to propose events, detects venue/schedule collisions, and routes to college administrators.
  • Inputs: Event details: title, startsAt, endsAt, venueName, capacity, categoryIds.
  • Processing: Verify caller is club manager. Compare [startsAt, endsAt] interval against all other events at the same venue. Flag overlaps in DuplicateReview. Transition status from DRAFT to PENDING_APPROVAL.
  • Outputs: Event draft; duplicate review notices in /college/approvals.
  • Error Handling: If endsAt <= startsAt: throw InvalidInputError("End date must be after start date.").

3.2.6 Poster Artwork Upload, S3 Storage & Tesseract OCR Pipeline

  • Introduction: Validates promotional artwork, uploads to private S3 buckets, and extracts text via OCR.
  • Inputs: Image file buffer, eventId.
  • Processing: Verify file size ≤ 4 MB. Verify binary magic bytes (JPEG/PNG/WebP). Prohibit SVG. Upload to private S3 bucket. Spawn Tesseract OCR worker to extract text and record suggestions.
  • Outputs: Stored EventPoster entity; extracted title, date, and venue suggestions.
  • Error Handling: Corrupt/disguised files throw InvalidInputError. OCR failure sets ocrStatus = 'FAILED' without aborting upload.
4

3.2.7 Cryptographic Attendance QR Issuance & Live Camera Scanning

  • Introduction: Issues dynamic HMAC-signed check-in passes and enables organizers to scan and mark attendance in real time.
  • Inputs: Registration ID for issuance; scanned QR token for check-in; status and reason for manual correction.
  • Processing: 1. Issuance: Sign token containing registrationId using HMAC-SHA256. Store token hash in AttendanceCredential.
    2. Scan: Verify signature. Verify check-in window: [startsAt - 2h, endsAt + 2h].
    3. Commit: Atomically update EventRegistration from CONFIRMED to ATTENDED and set checkedInAt = NOW(). Log ATTENDANCE_RECORDED audit entry.
  • Outputs: Success verification banner with student name and roll number; updated attendance metrics.
  • Error Handling: Expired tokens return 400. Duplicate check-in scans return 409 (ALREADY_CHECKED_IN).

3.2.8 Verified Attendee Feedback & Comment Moderation

  • Introduction: Collects star ratings and qualitative reviews exclusively from verified attendees.
  • Inputs: eventId, rating (1–5), comment (optional), isPublic.
  • Processing: Verify caller has EventRegistration with status === 'ATTENDED'. Verify event ended and within 30-day window. Insert Feedback in PENDING status.
  • Outputs: Recorded Feedback entity; aggregated rating analytics for clubs.
  • Error Handling: Unattended students attempting feedback receive ActorNotAuthorizedError (403).

3.2.9 In-Database Token-Bucket Rate Limiting & Sensitive Data Exports

  • Introduction: Protects endpoints against automated attacks and exports formula-injection-safe CSVs.
  • Inputs: Action key, user identifier, export query parameters.
  • Processing: Atomically consume tokens from RateLimit table; fail closed on error. For CSV exports: prepend tab to cells starting with =, +, -, or @. Log EXPORT_DOWNLOADED audit entry.
  • Outputs: Rate limit approval or 429 Retry After; streaming CSV download.
  • Error Handling: Unauthorized export attempts return HTTP 403.

3.5 Non-Functional Requirements

3.5.1 Performance

  • Server Response Latency: 95% of Server Component page renders shall deliver the first contentful paint in under 800 ms.
  • Database Queries: 95% of indexed queries shall execute in under 50 ms via Prisma connection pooling.
  • Live Camera Scanning: The camera QR scanner shall decode, verify, and commit attendance check-ins in under 250 ms per attendee.
  • Build Optimization: Next.js Turbopack production compilation shall complete within 40 seconds.

3.5.2 Reliability

  • Atomic Transactions: Multi-table state mutations shall execute inside PostgreSQL transactions (runInTransaction), guaranteeing zero partial states on crash.
  • Fail-Closed Security: Rate limiters and authorization guards shall fail closed upon database timeouts.
  • Idempotency: Repeated submission of identical mutations shall be handled cleanly without unhandled server exceptions.

3.5.3 Availability

  • Target Uptime: Target 99.9% availability backed by Vercel serverless edge nodes and Neon multi-AZ failover.
  • Automated Health Monitoring: /api/health shall verify live database connectivity (SELECT 1) within 100 ms.

3.5.4 Security

  • Password Hashing: Strictly Argon2id with memory-hard cost parameters. No plaintext passwords logged.
  • Tenant Isolation: Foreign-key scoping on all 19 tables; cross-tenant requests return HTTP 404 (TenantIsolationError).
  • Dynamic QR Credentials: HMAC-SHA256 signed tokens bound to specific registrations, valid only within a 4-hour window.
  • Instant Session Purging: Role modifications or tenant suspensions immediately delete all corresponding database sessions.

3.5.5 Maintainability

  • Type Safety: 100% strict TypeScript typing (tsc --noEmit) with zero compiler errors.
  • Automated Testing: Test suite maintaining 32 test files and 246 automated tests passing with zero failures.

3.5.6 Portability

The system shall execute without code changes in any Node.js ≥ 20.19.0 runtime, Docker container, or Vercel serverless environment.

3.7 Design Constraints

Constrained strictly to free-tier cloud resources: Vercel Hobby + Neon PostgreSQL Free (0.5 GB) + Supabase Storage Free (1 GB). No paid external APIs are utilized.

3.9 Other Requirements

Maintains an immutable transactional audit trail (AuditLog) for every critical action with sensitive fields redacted. Frontend complies with WCAG 2.1 AA accessibility standards.
